CI Was Becoming a Mess

November 2026

97%of a check is the tests

Once coding agents started doing real work, the slow part of shipping stopped being the writing. An agent finishes a change in a few minutes, and then it waits on CI for longer than it took to write the code. Run five or eight agents at once and the waiting turns into a queue, every pull request gets tested on its own, then tested again after it is rebased onto main, and two changes that each passed can still break main together.

I have been building land to fix this, and this post is about the technical decisions behind it and what the measurements taught me along the way, including the ones that did not flatter us.

Merge by function, not by line

Git merges text line by line, so two agents editing different functions in the same file still collide. land merges with weave, which parses each file into functions, classes and methods and merges them one by one. Two edits to different functions combine cleanly, and two edits to the same function come back as a conflict that names that function, so nothing is ever guessed.

git merge
billing.py
billing.py @@ -12,6 +12,9 @@ <<<<<<< agent-a +def refund(order): ... ======= +def discount(order): ... >>>>>>> agent-b CONFLICT both added at the same line
weave
billing.py
billing.py + refund function agent-a + discount function agent-b ✓ merged 2 entities, no overlap tests run once on the result

Test the merged result once

The biggest waste in a normal setup is testing each pull request separately and then again after every rebase. land merges all the finished branches onto the latest main and runs the tests once on the combined result. If something fails, it finds the branch responsible by looking at what the failing test actually read, drops only that branch, and lands the rest.

Let your setup script define the environment

I stopped trying to guess how anyone's project installs. You write a small setup script, land runs it once on a throwaway machine, and whatever it leaves behind is the environment. While it runs, land records every file of your repo the script looked at, and it reuses that environment until one of those files changes.

This is where I learned my first lesson the hard way. On NetworkX a one line change took 276 seconds, because the obvious pip install -e . touches every source file, so every edit looked like a dependency change and the environment was rebuilt each time. Installing only the dependencies brought the same change down to 84 seconds without touching the engine at all.

.land/setup.sh
@@ install only what the tests need @@ - pip install -e ".[default,test]" # reads every source file + pip install numpy scipy pandas pytest pytest-xdist + pip install ./stub # metadata and entry points only one line change to main 276s → 84s

Only rerun what a change can reach

While each test command runs, land records every file it reads. On the next merge a command reruns only if one of those files changed, and results are stored against exactly what was read, so the same code coming back after a rebase reuses its earlier result instead of running again. This works per test command today, so a monorepo gets the most out of it with one command per package.

Isolation that strangers' code can trust

land runs other people's setup scripts and tests, so every check runs in its own Firecracker microVM, offline and as an unprivileged user, and the machine boots in about half a second. A test that fails and then passes on the same code is refused as flaky instead of being retried until it goes green, a change that deletes or skips a test is refused, and main only moves with a signed statement of exactly what passed.

Then I profiled it

When I profiled a land check end to end, almost all of the time, about 97 percent, was the test suite itself. Boot took half a second, the environment cost nothing because it was reused, and packing results took a couple of seconds. So I went looking at the hardware, and ran the same suite on bare cloud machines and inside our own runner.

same 9,444 tests · 4 workers · median of 2 runs
█████████ 27s AMD EPYC running directly ██████████████ 42s Intel Xeon running directly ██████████████████████████ 78s our runner VM inside a VM, plus tracing

Faster cores won back about fifteen seconds, but the layers around the tests cost more than twice that. Our microVMs were running inside rented cloud VMs, which means every check paid for virtualization twice. The isolation is not negotiable when you run other people's code, but the nesting is, so the next step is running the microVMs directly on bare metal AMD machines.

What I am still honest about

On a single fresh change, land is not the fastest today, because a dedicated fast runner beats our nested setup on raw hardware. Where land wins clearly is the case that is becoming normal, several agents finishing at once, where checking the merged result once used a fraction of the compute of every merge queue I measured. The two things left to make it fast everywhere are better hardware and running only the individual tests a change can reach, and I am working on both.

The whole thing is priced per change that lands on main rather than per CI minute, because I wanted the incentive to be doing less work, not more.
